Lesson 4

Talking to the gateway API

Every interaction with the gateway is an HTTP request from your server. Getting the basics right (keys, headers, errors, timeouts, retries) prevents most production incidents.

The headers on every request

Headers are labels on the outside of an HTTP request, separate from the JSON body. Two say who you are; the others control how the request is handled. 

x-client-id:       your app ID          ← like a username
x-client-secret:   your secret key      ← like a password
x-api-version:     2026-01-01           ← which version of the API
x-request-id:      9f2c…  (optional)    ← your tracking ID for this call
x-idempotency-key: 47bf…  (optional)    ← "this is a retry of the same request"
Content-Type:      application/json
HeaderRequired?Why it exists
x-client-idYesIdentifies your merchant account. Found in the gateway dashboard.
x-client-secretYesProves it's really you. Anyone with this can act as your business.
x-api-versionYesFixes the request and response format, so the gateway's changes don't break you.
x-request-idNoAn ID you choose. Log it; give it to gateway support so they can find the exact call.
x-idempotency-keyNoMakes retries safe. It gets its own lesson (Lesson 5).

Keeping keys safe

  • Server only. The secret must never be in frontend code, a mobile app bundle, or anything a user can download.
  • Environment variables or a secrets manager, never committed to git.
  • Different keys per environment. Sandbox keys only work with the sandbox URL; live keys only with production.
  • Never log them, even in error logs. Mask headers in any request logging.
  • Rotate them if they ever leak or someone with access leaves.
  • The same secret often signs webhooks. If it leaks, attackers can also forge "payment successful" messages to you.

API versions

Gateways change field names and response shapes over time. The version header lets you pin the format you built against. Upgrade on purpose, test in sandbox, then switch.

Read field names exactly

Small differences matter. For example, Cashfree's request uses authorization_details (with a z), while the response uses authorisation_details (with an s). Read the wrong one and you silently get undefined. Copy names from the docs for the exact version you pin.

HTTP status codes and what to do

Each response comes with a status code. Each code calls for a different reaction:

CodeMeansTypical causeRetry?Action
200SuccessNormal—Validate the body, then continue.
400Bad requestInvalid phone or email, duplicate ID, wrong fieldNoFix the input. Show the user a clear message.
401Authentication failedWrong keys, or sandbox keys used against productionNoAlert yourself: config is broken for everyone.
404Not foundUnknown plan or subscription IDNoUsually a setup error; alert.

Simple rule: 4xx = your problem (don't retry; fix it). 5xx, 429 or no response = maybe temporary (retry safely).

Timeouts: the "unknown" outcome

Always set a timeout (for example 10–15 seconds). Without one, a hung connection can block a request forever.

But understand what a timeout means:

A timeout doesn't mean the request failed. It means you don't know whether it succeeded.

The gateway may have created the subscription and the response got lost on the way back. You have three options:

  1. Retry with the same idempotency key. If it was created, the gateway returns the original result. (Lesson 5)
  2. Fetch by your own ID. Ask "do you have subscription X?" before creating again.
  3. Give up and use a new ID. The old one, if it exists, is never paid and expires on its own. That's safe for creating; it's not safe for actions that move money.

When to retry

SituationRetry?How
Timeout or connection resetYesSame idempotency key, short delay
5xx from the gatewayYesSame key, exponential backoff (e.g. 0.5s, 1s, 2s)
429 rate limitLaterWait (check any retry-after header); don't hammer
400 / 401 / 404 / 422NoRetrying gives the same answer
  • Keep it small: 1–3 attempts. The user is waiting.
  • Add jitter (a small random extra delay) so thousands of clients don't all retry at the same instant after an outage.
  • Never retry money-moving calls (charges, refunds) without an idempotency key.

Don't pass the gateway's errors to your users

It's tempting to return whatever the gateway returned. Don't. A gateway 401 means your server's keys are wrong, but if you send 401 to your frontend, it thinks the user's login expired. It may log them out, or refresh the token and repeat the request (creating another subscription).

Gateway saidYou return to your appUser sees
400 because of user input400 with a clear message"Please add a valid 10-digit mobile number."
401, 404, 422 (your setup)502"Payment provider issue, please try again."
429503"Busy, try again in a minute."
5xx or timeout502"Payment provider issue, please try again."

Keep the gateway's full error body in your logs, not in the response. Never send database or internal error messages to the client either.

Rate limits

Gateways limit how many requests you can make per second or minute, usually for your whole merchant account, not per customer.

Edge case: one user can block everyone

If a single user (or a bot) hits your "create subscription" endpoint in a loop, they use up your account's limit. Then every customer gets 429 errors. Protect yourself with a per-user limit (e.g. 5 creates per 10 minutes), and reuse a recent pending subscription instead of creating a new one (Lesson 6).

Why "keep-alive" matters

Every new HTTPS connection costs a handshake: several round trips before any data moves, often 100 ms or more. By default some HTTP libraries open a fresh connection per request. A keep-alive agent reuses open connections, so later calls skip the handshake. At high volume this saves real latency and server resources.

Logging

For each gateway call, one structured log line is worth more than ten scattered console.logs:

  • Log: your order ID, the gateway's ID, your request ID, the endpoint, status code, how long it took, and the user ID.
  • Mask: phone numbers, emails and names (personal data).
  • Never log: secret keys, full card numbers, auth headers.
Tip: alert on configuration errors

A burst of 401 or 404 responses means something is misconfigured (keys, plan IDs, environment) and every payment is failing. These should page someone, not sit quietly in a log file.
