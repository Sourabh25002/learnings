Lesson 7

Verifying a payment

The customer is back from checkout. Two questions remain: did they really pay, and if so, how do we give them what they paid for exactly once, even if everything arrives twice?

What verify is for

Verify is a receptionist at a members-only door. A person walks up and says "I've paid". The receptionist doesn't take their word for it. They call the bank, hear the real answer, and only then stamp the membership card, once, even if the same person (or a colleague) asks again a second later.

Verify exists for the user's experience: they see "Payment successful" the moment they come back, instead of waiting for a webhook. It's one of the two ways back from Lesson 3. The webhook is the other, and both must be safe to run together.

The return handler

Before verify, there's a tiny endpoint the gateway redirects the browser to. Its only job is to send the user to the right page:

  1. Read your order ID from the URL (or the posted form; accept both GET and POST).
  2. Redirect to your app's payment-result page with that order ID.
  3. If the order ID is missing, still redirect to a real page (e.g. the subscription page), never a 404.

It does not decide anything about money. Anyone can open that URL. The page it redirects to then calls verify.

Verify, step by step

  1. Who is asking? The user comes from the login token, never from the request body.
  2. Is this order theirs? Look up the order by your order ID and this user. Not found → 404. Nobody can verify (or peek at) someone else's order.
  3. Already settled in our records? If it's already granted, answer "success" straight away. This makes repeated calls (refreshes, double calls) cheap and harmless.
  4. Ask the gateway Fetch the real status: Fetch Subscription for subscriptions, Get Order for one-time orders. It's a read, so retrying is safe and no idempotency key is needed.
  5. Check the answer makes sense A status is present, the ID matches, and for one-time orders the amount and currency match what you stored when you created it.
  6. Classify: success, pending, or failed Only final statuses lead to a decision (next section).
  7. Success → grant exactly once An atomic "only if not already granted" update or a lock. See Granting exactly once.
  8. Record the payments Add each gateway payment to your ledger, keyed by payment ID. If this fails, verify still succeeds.
  9. Failed (final) → mark this order only Never touch the user's access from other purchases.
  10. Pending → change nothing Reply "pending" so the frontend can check again.
  11. Reply with a clear state success, pending or failed, plus a friendly message.

Final vs not-final statuses

The most important idea in this lesson:

Only decide on final answers. "Not finished yet" is not "failed".

A subscription in INITIALIZED could mean the customer gave up, or that they're approving the UPI AutoPay request on their phone right now. One check can't tell the two apart, so you wait for something definite.

Where do final answers come from, if not from verify? Webhooks (Lesson 8) and the session expiry deadline: after the checkout link expires, an unfinished subscription can never complete, so a cleanup job can safely mark it abandoned.

"Still in progress": what the user sees

UPI and card approvals usually finish within seconds. So the frontend does a short, polite wait:

  1. Show "Confirming your payment…".
  2. Call verify again every 3–5 seconds, for about a minute.
  3. Becomes success: "Payment successful 🎉", then refresh the user's plan.
  4. Still pending after a minute: "We haven't received confirmation yet. If you completed the payment, your plan will activate automatically in a few minutes." The webhook will finish the job.
  5. Final failure: "Payment wasn't completed. You haven't been charged for this attempt." Offer a retry button.
Tip: eNACH needs different words

Bank mandates can take much longer than a minute. If the method was eNACH, say "Your bank is confirming the mandate. This can take a while; we'll update your plan automatically."

Granting exactly once

The return and the webhook often arrive within the same second. If both read "not granted yet" and then both grant, the user gets two months, or two coupons. Reading first and writing second is the bug; the fix is to make check-and-write a single step.

Three tools for "exactly once"

ToolUse it whenHow
Conditional updateGranting is one row changeAdd "and not already granted" to the WHERE. Act only if 1 row changed.
LockGranting is several steps (order row, user row, emails)Lock on the order ID (DB named lock, or SELECT … FOR UPDATE in a transaction), check, do all steps, unlock.
Unique keyEach grant matches one thing (a payment, a coupon)Insert the payment ID or order ID into a UNIQUE column. A duplicate insert means "already done".

Both callers can tell their own caller "success". Only one of them actually changes anything.

Watch out: "add a month" vs "set until"

expiry = expiry + 1 month is dangerous: running it twice gives two months. expiry = start of period + 1 month is naturally safe to repeat. When you can, write updates that give the same result however many times they run.

Recording the payments

After a successful grant, ask the gateway for the list of payments (e.g. "fetch all payments of this subscription") and store each one:

  • Keyed by the gateway's payment ID (UNIQUE). Seeing the same payment again just updates its status; no duplicate rows.
  • Store amount, status, method (UPI / card / eNACH), AUTH or CHARGE, failure reason, and which order or subscription it belongs to.
  • Best effort. If this extra call fails, verify still succeeds. The webhook or a later sync fills the gap. The customer should never see an error because a receipt couldn't be fetched.

Things verify must never do

Never
  • Grant because the URL says so. Only the gateway's answer counts.
  • Treat "not finished" as "failed". The user may be mid-approval.
  • Downgrade the user because one order failed. A failed or abandoned new attempt says nothing about access they already paid for. Mark the order, not the person.
  • Extend access twice for the same payment, from verify, webhook, refresh or retry.
  • Pass the gateway's error codes through to the user (see Lesson 4).

Why "failed" can still be HTTP 200

The request worked: you successfully found out the payment failed. Keeping HTTP errors for "the request itself broke" makes the frontend simpler. Choose one convention and use it everywhere.

The frontend side

  • Read the order ID once, then remove it from the URL using your router's navigate/replace, not window.history directly. Otherwise the router still "sees" the old URL, and moving between tabs or refreshing triggers verify again.
  • Don't run verify twice in parallel (e.g. on mount and on a re-render). Guard it with a flag.
  • Refresh the user's data after success so the new plan shows everywhere.
  • Mobile apps: make sure the return actually lands back inside the app (deep link or native SDK). See Lesson 3.
