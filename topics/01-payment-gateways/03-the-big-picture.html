Lesson 3

The end-to-end flow

This is the map for the rest of the chapter: every step from the customer clicking "Subscribe" to them getting access, and every month after that.

The golden rule

Never believe the browser about money. Only believe what the gateway tells your server directly.

Everything that happens in the customer's browser can be faked or can simply fail:

  • Anyone can type ?payment=success into a URL.
  • Your frontend code can be edited in dev tools to "send" any amount or plan.
  • The customer can close the tab one second after paying.

So the browser's job is only to start things and show results. Every decision about money or access is made on your server, using information it gets from the gateway directly (server-to-server).

The full flow, step by step

Starting the payment (steps 1–7)

  1. Customer clicks "Subscribe" The browser sends only which plan (e.g. STARTER_MONTHLY). Never a price. The server knows who the user is from their login token.
  2. Your backend asks the gateway to create the subscription With your secret keys, from your server. Lesson 6 covers everything that must happen before this call.
  3. The gateway returns a session ID A short-lived token that lets one browser open checkout for this one subscription. It isn't a secret key, so it's safe to send to the browser.
  4. Your backend saves a PENDING record Before replying to the browser. This guarantees you never have a payment you don't know about.
  5. The browser receives the session ID Plus whether it's sandbox or production, so the SDK opens the right checkout.
  6. The browser opens the gateway's checkout Using the gateway's JavaScript SDK, e.g. subscriptionsCheckout({ subsSessionId }). The customer is now on the gateway's page, not yours.
  7. The customer approves UPI PIN, card OTP or bank login. Your app sees none of this.

Getting the result back (paths A and B)

Path A, return + verify: the gateway sends the browser to your return URL. Your app then asks your backend "please verify order X", and your backend fetches the real status from the gateway. It never trusts the redirect itself.

Path B, webhook: the gateway's server calls your server directly with a signed message. You check the signature (proof it really came from the gateway), then act. Webhooks also deliver everything that happens later: monthly charges, failures, cancellations.

Why there are two ways back

Each path fails in situations where the other one still works:

SituationPath A (return)Path B (webhook)
Customer closes the tab right after payingNever happensStill arrives
Phone switches to the UPI app and never comes backNever happensStill arrives
Webhook is delayed for minutesCustomer sees the result immediatelyLate
Your webhook endpoint was downStill worksGateway retries later
Monthly renewal, cancellation from a UPI appCustomer isn't involvedOnly way to know
Edge case: both paths arrive at the same moment

This is common: the customer returns and the webhook lands within the same second. If both check "has access been granted?", both see "no" and both grant it, you can end up extending access twice or writing duplicate records. Granting must happen exactly once: use a database lock or an atomic update such as "set to ACTIVE only if not already ACTIVE".

The return URL, properly

The return URL is where the gateway sends the browser after checkout. Things to know:

  • It carries no login. The request comes from a redirect, often without your auth token. So put your order ID in the URL to know which payment it's about. Never put anything secret there.
  • It isn't proof of payment. Anyone can open that URL. It only means "go and check"; your server then fetches the real status.
  • Build it from config, not from the incoming request. Behind a load balancer, your server may think it's on http:// or an internal hostname. Use a fixed setting like API_BASE_URL=https://api.yourapp.com.
  • It can arrive as GET or POST. Some gateways post form data to it. Accept both.
  • Always redirect somewhere real. Every branch, including "order ID missing", must land on a page that exists, never a 404.
  • Clean up afterwards. Once the frontend has read order_id from the URL, remove it (through your router, not around it). Otherwise a refresh or navigation verifies again.

Mobile apps and webviews

If your app runs inside a webview (Capacitor, Cordova, React Native WebView), the checkout and the return need extra care:

  • The webview may open the gateway's page in the system browser. The return URL then lands in the browser, not your app, where the user isn't logged in.
  • Fixes: use the gateway's native SDK for Android/iOS, or an in-app browser plus a deep link that brings the user back into the app.
  • Either way, the webhook still grants access. So the user has paid; they just see a confusing screen. Test this flow on a real device.

What you store

Two tables cover most needs:

Subscriptions (one row per subscription)

  • your subscription ID (unique)
  • the gateway's subscription ID
  • user, plan, amount, currency
  • gateway status (raw string) + your own status
  • paid-until / expiry date
  • created, updated, cancelled timestamps

Payments ledger (one row per payment)

  • the gateway's payment ID (unique)
  • which subscription it belongs to
  • AUTH or CHARGE, amount, status
  • payment method (UPI, card, eNACH)
  • failure reason, if any
  • billing period it covers
Tip: keep the raw status

Store the gateway's exact status string (ACTIVE, ON_HOLD…) as well as your own simplified status. When something looks wrong months later, the raw value tells you exactly what the gateway said.

Payment status vs access

"Is the subscription active?" and "should this user see Pro features?" are different questions:

  • A cancelled subscription can still give access until the end of the period the customer paid for.
  • An active subscription might belong to an old plan, not the one giving current access.
  • Access may also come from somewhere else: a free trial, or a family member's plan.

A clean design keeps payment records as the history and derives access from them ("paid until date X for tier Y"). Then access checks can be simple and fast.
