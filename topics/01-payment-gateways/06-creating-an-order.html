Lesson 6

Creating an order, safely

"Create order" is the first server-side step of every payment, and the one that has to work for millions of clicks without ever creating duplicates, charging the wrong price or leaving the customer stuck. This lesson walks through a complete, production-grade design.

Order or subscription?

Everything here applies to both. One-time payments call it an order; recurring ones call it a subscription. The steps are the same; a subscription just has a plan and a mandate attached.

The 12 steps at a glance

  1. Authenticate Know who the user is from their login token, never from a userId in the request body.
  2. Rate-limit A few creates per user per few minutes. Protects your account-wide gateway limit.
  3. Validate the plan, look up the price The client sends only a plan key. The price comes from server config.
  4. Take a per-user lock So two clicks or two tabs can't both get through steps 5–10 at the same time.
  5. Check eligibility Already subscribed? Recent unfinished checkout to reuse? Trial user?
  6. Prepare customer details From your database. Normalise the phone, check email and name.
  7. Build the request Your unique ID, return URL from config, session expiry, auth amount, first charge time, tags.
  8. Call the gateway Through the shared client: timeout, idempotency key, safe retry.
  9. Validate the response Session ID, gateway ID and status must all be present.
  10. Save the pending record Before replying. Store your ID, the gateway's ID, session ID, plan, amount and status.
  11. Release the lock and respond Send only what the frontend needs. Map errors to friendly messages.
  12. Log and measure One structured log line, plus metrics and alerts.

The rest of the lesson explains the steps that need real thought.

Price comes from the server

The frontend sends { planType: "STARTER_MONTHLY" }, never { amount: 499 }. If you accept an amount from the browser, someone will send amount: 1.

  • Look up the plan in server config. Reject unknown keys with a clear 400.
  • Check that the plan can be bought this way (e.g. monthly subscriptions only).
  • One source of truth. The amount you store must equal the amount the gateway charges. Build the plan inline from your config, or check on startup that the gateway's plan amounts match.
  • Store money safely: DECIMAL or integer paise, never floats, plus the currency.
Edge case: test prices in production

₹1 plans are handy in sandbox and a disaster in production. Make "prices match the real price list" a go-live checklist item, or fail startup if production config has suspicious amounts.

Stopping duplicates: locks

"Check if the user already has a pending subscription, and if not, create one" sounds safe. It isn't, when two requests arrive together: a double-click, two open tabs, or a retry from a flaky network.

How to lock (context)

OptionHow it worksNotes
Database named lockMySQL GET_LOCK('sub_create_42', 5) … RELEASE_LOCK(…). Only one connection can hold that name at a time.No extra infrastructure. Released automatically if the connection dies. Use the same connection for get and release.
Redis lockSET lock:sub:42 <token> NX PX 30000: set only if it doesn't exist, with expiry.Works across many servers. The expiry (TTL) frees it if a server crashes.
Unique constraintThe database refuses a second "pending" row for the same user.The strongest final safety net. Combine with a lock for a clean user experience.
  • Lock per user, not globally. Different users never wait for each other.
  • Always release in a finally block, and always have a timeout or TTL so a crash can't hold it forever.
  • Holding it during the gateway call is fine. It's per user, and the whole point is to cover check → create → save.
  • If the lock is busy, wait a few seconds, then either continue (and likely reuse the pending one) or answer "already in progress".

Eligibility: should this user subscribe now?

Inside the lock, decide what to do based on the user's current state:

User's situationWhat to do
No subscriptionCreate a new one.
Already has an active paid subscriptionReject: "You're already subscribed." Plan changes need their own upgrade or downgrade flow, never a second mandate.
Pending one for the same plan, session still validReturn the same session ID. To the user this feels like "it just worked"; no new subscription.
Pending one for a different planCreate a new one; the old one expires unused. (Optionally cancel the old one.)
On a free trialAllow. Decide whether paid access starts now or when the trial ends.
Cancelled but paid period not overAllow, but decide the start date so they don't pay twice for the same days.
Has access through someone else (e.g. family plan)Product decision: allow or explain why it isn't needed.
Tip: reuse needs the session saved

To reuse a pending checkout, you must store its session ID and creation time (step 10), and know when sessions expire (step 7).

Customer details

The gateway needs name, email and phone for the checkout page and for pre-debit notifications.

  • Take them from your database, not from the request body. Otherwise a client can register any phone or email on the mandate, and notifications go to the wrong person.
  • Validate before calling the gateway, so the user gets a clear message instead of a vague provider error.

Building the request

Your unique ID

Example: sub_42_1717171717123_9f3a

  • A prefix (sub_, slot_, coupon_) tells you what kind of payment it is when it shows up in a webhook or log.
  • User ID + timestamp make it readable and roughly sortable.
  • A random suffix prevents two requests in the same millisecond getting the same ID.
  • Respect the gateway's rules: allowed characters (letters, digits, _ - .) and maximum length.

Return URL

  • Built from a configured base URL (API_BASE_URL=https://api.yourapp.com), never from the incoming request's host or protocol.
  • Always https.
  • Includes your order ID, so the return handler knows what to verify. Nothing secret.

Session expiry

Set it explicitly (e.g. 30 minutes). Short-lived checkout links mean abandoned subscriptions expire quickly, and they give a clear rule for "is this pending one still reusable?".

Auth amount and first charge time

Decide them together so month 1 is charged exactly once for every payment method, including eNACH. See the first-month trap.

The rest

  • Payment methods: only the ones you've tested (e.g. UPI, card, eNACH).
  • Notification channels: SMS and/or email for pre-debit notices.
  • Tags: user ID, plan key, environment. They come back in webhooks and help with debugging.
  • Plan: a plan_id created once per environment, or the plan inline from your config. Inline keeps the price in one place.

Calling the gateway

This step is short because Lessons 4 and 5 did the work:

  • Go through the shared gateway client: config-driven URL and keys, version header, keep-alive, one error mapper.
  • Timeout on the call (10–15 s).
  • One idempotency key per create attempt, reused only if you retry that same request.
  • Retry only timeouts, network errors and 5xx, once or twice with a short backoff. Never 4xx.
  • Send an x-request-id (e.g. your order ID) so support can find the call.

Validate the response

A 200 isn't enough. Check that the body has everything you need:

  • session ID (to open checkout)
  • the gateway's subscription ID (to match webhooks later)
  • a status, normally INITIALIZED

If anything is missing, treat it as a provider failure: log the full body, return a friendly error, don't save a half-record.

Save first, then reply

Never give the customer a way to pay for something your database doesn't know about.

The order is: gateway creates → you save → you send the session ID. If the save fails, you don't send the session ID. The customer can't pay, and the subscription at the gateway just expires unused. If you replied first and saved second, a failed save would leave a paid subscription with no record. Then your webhooks find nothing, and the customer paid for nothing.

Save: your ID, the gateway's ID, user, plan, amount, currency, session ID, session expiry, status (PENDING plus the raw gateway status), and timestamps.

Responding to the frontend

  • Success: only the session ID, the mode (sandbox or production, so the SDK opens the right checkout), and your order ID.
  • User-fixable errors (400): a specific message, e.g. "Please add a valid mobile number to your profile."
  • Provider or setup errors: 502 (or 503 for rate limits) with a generic "payment provider issue" message. Never pass the gateway's 401 through.
  • Never leak internals: no SQL errors, stack traces or raw gateway bodies.
  • Frontend side: disable the button while the request runs, so a double-click is stopped before it even reaches the server lock.

Observability

One log line per create

event=subscription_create  user=42  order=sub_42_…_9f3a  cf_id=4567
plan=STARTER_MONTHLY  outcome=created|reused|rejected|provider_error
http=200  latency_ms=840  request_id=…

Metrics worth watching

  • Creates per minute, and the split between created, reused and rejected
  • Gateway latency (p95) and error rate by status code
  • 429 count (are you near the rate limit?)
  • Checkout conversion: created vs actually activated

Alerts

  • Any burst of 401 or 404 from the gateway: config is broken for everyone
  • Error rate above normal for several minutes
  • Database save failures after a successful gateway create

Go-live checklist

  • Production plans exist, and their prices match the real price list
  • No test prices (₹1) left in production config
  • Live keys, production base URL and environment name all switch together
  • Return URL uses the production https domain
  • Webhook URL configured in the production dashboard
  • Session expiry, rate limit and per-user lock enabled
  • Double-click and two-tab test: only one subscription created
  • Each payment method tested in sandbox (UPI, card, eNACH), checking exactly when month 1 is charged
  • Abandoned checkout tested: no access change, pending row expires
  • Mobile app tested on a real device: user ends up back in the app
  • Alerts for gateway 401/404 and save failures
  • Logs mask phone and email; no secrets anywhere in logs
What comes after this

Creating the order only starts the payment. The next lessons, verifying the result and handling webhooks, are where access is actually granted. They need the same "exactly once, no matter what" thinking.
