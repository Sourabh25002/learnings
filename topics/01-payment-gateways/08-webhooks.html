Lesson 8

Webhooks

A webhook is the gateway calling you. It's the only way to hear about things that happen when the customer isn't on your site: monthly charges, failures, cancellations from a UPI app. It's also the safety net when the browser never comes back.

What a webhook is

Normally your server calls the gateway. A webhook is the reverse: when something happens, the gateway sends an HTTP POST to a URL on your server, with a JSON body describing the event.

Polling is calling the courier every 10 minutes asking "is my parcel here yet?". A webhook is the courier ringing your doorbell when it arrives. But anyone can ring a doorbell, so you must check who's at the door before opening it.

Setting it up

  • One URL per environment, set in the gateway dashboard: sandbox points at your test server, production at your live one.
  • Public and https. The gateway must be able to reach it. It must not require your users' login token, because the gateway has none. Security comes from the signature instead.
  • Choose the webhook version that matches your API version, so payload fields match the docs you read.
  • Subscribe to the events you need (subscription events, and payment events for one-time orders).

The handler in four steps

Step 1: check the signature

Your webhook URL is public. Anyone who finds it could POST {"type": "PAYMENT_SUCCESS", …}. The signature proves the message really came from the gateway and wasn't changed on the way.

How it works (in plain words)

  1. You and the gateway share a secret (usually your API secret key).
  2. The gateway mixes the secret with the exact message (timestamp + body) using HMAC-SHA256, a one-way "fingerprint" function. It sends the result in a header, e.g. x-webhook-signature, plus the timestamp in x-webhook-timestamp.
  3. You compute the same fingerprint yourself from the timestamp, the body you received and your copy of the secret.
  4. They match: it's genuine. They don't: reject it.

It's a wax seal that only you and the gateway know how to make. A forger can copy the letter, but without the secret they can't produce the right seal, and if they change one word, the seal no longer matches.

Getting it right

  • Use the raw body, byte for byte. If your framework parses the JSON and you re-stringify it, spacing or key order can change, and the fingerprint won't match. Capture the raw body before parsing.
  • Missing signature headers = reject. Never "process anyway". That would let anyone forge an event just by leaving the headers out.
  • Missing raw body or secret on your side = reject (and alert). It's a bug or misconfiguration, not a reason to skip security.
  • Check the timestamp is recent (e.g. within 5 minutes). This blocks replay attacks: someone capturing a real, correctly signed webhook and re-sending it later.
  • Compare in constant time (e.g. crypto.timingSafeEqual) so attackers can't learn the signature from response timing.
Edge case: the free-renewal attack

If unsigned webhooks are accepted, a user who knows their own subscription ID (it's in their browser) can POST a fake "monthly charge succeeded" event, again and again, and get months of access for free. Signature checking isn't optional.

Step 2: store the event

Before doing any work, save the event to an inbox table:

ColumnWhy
event_key (UNIQUE)Something that identifies this event, e.g. a gateway event ID, or a hash of type + IDs + payment status. A duplicate insert means "seen it already".
typee.g. SUBSCRIPTION_PAYMENT_SUCCESS
raw_bodyThe exact payload, for debugging and re-processing
received_at / processed_atWhen it came in, when it was handled
status + attempts + last_errorpending / done / failed, so failures can be retried by a job

What this gives you:

  • Nothing is lost. If processing crashes, the event is still saved and can be retried.
  • Duplicates are easy to spot. The unique key catches them.
  • An audit trail. "What exactly did the gateway tell us on 3 March?" has an answer.
  • Replay. After fixing a bug, re-run the stored events.

Step 3: reply fast

The gateway waits only a few seconds for your reply. If you're slow, it marks the delivery as failed and sends it again later. Slow handlers therefore create their own duplicates.

  • Reply 200 as soon as the event is safely stored.
  • Do the heavy work (calling the gateway API, updating the database, sending emails) after replying: in a background job or queue, or at least without blocking the response.
  • Small apps often process inline and reply after. That's fine while processing is quick and the inbox exists as a backup.

Step 4: process it

  1. Route by event type Subscription events and one-time payment events go to different handlers. For one-time orders, route by your order ID prefix (e.g. slot… → family slots, rptc_… → coupons). This is why prefixes matter (Lesson 6).
  2. Find your record By your own ID first, then by the gateway's ID. Not found? Log it and acknowledge: it may be an abandoned attempt that was never saved, or another environment's event.
  3. Re-fetch the real status Ask the gateway for the current state instead of trusting the payload alone. This fixes out-of-order delivery: you always act on the latest truth, not on whichever event happened to arrive last.
  4. Apply exactly once Same tools as verify: a conditional update, a lock, or a unique key per payment ID (Lesson 7).
  5. Mark the inbox row done Or failed, with the error, so a retry job can pick it up.

Delivery reality: late, twice, out of order

Every webhook can arrive late, more than once, out of order, or not at all. Design for all four.

What happensWhyYour defence
DuplicatesGateway retries after a slow or failed reply; network quirksInbox unique key; per-payment unique key; conditional updates

What to reply when something breaks

Your reply code tells the gateway whether to try again. Choose deliberately:

SituationReplyWhy
Stored (and processed) fine200Done.
Duplicate we've seen200Don't make them retry something already handled.
Bad or missing signature401 / 400Not from the gateway; nothing to retry.
Unknown order / irrelevant event200Retrying won't change anything.
Couldn't even store it (database down)500You want a retry. It's the only copy.
Stored, but processing failed200It's safe in your inbox; your own retry job handles it.
Watch out: "always reply 200"

Replying 200 even when you couldn't store or process an event avoids retry storms, but silently loses the event. That's only acceptable if you've stored it first. The inbox is what makes "200 on processing errors" safe.

Monitoring and testing

Monitor

  • Events received per type per hour, and signature failures (a spike may mean an attack, or a rotated secret).
  • Inbox backlog: events stuck in pending or failed.
  • Silence: zero webhooks for hours when you normally get some usually means the URL or configuration broke. Alert on it.

Test

  • Use the gateway's sandbox to trigger real events. For local development, a tunnel (e.g. ngrok) gives your laptop a public URL.
  • Send the same event twice: nothing should change the second time.
  • Send events in the wrong order: the final state must still be right.
  • Send an event with a bad or missing signature: it must be rejected.
