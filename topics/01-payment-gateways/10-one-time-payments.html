Lesson 10

One-time payments: add-ons and coupons

Not everything is a subscription. "Unlock one more family slot for ₹1,500" or "buy one extra report for ₹999" are one-time purchases. They're simpler (no mandate, no renewals), but they have their own traps, mostly around delivering what was bought exactly once.

The order flow

It's the same shape as a subscription (Lesson 3), just with an order instead of a mandate:

  1. User clicks "Buy" Sends what they want (e.g. "slot 3"), never a price.
  2. Backend checks eligibility, then creates the order Calls the gateway's Create Order API with the amount from server config and a prefixed order ID like slot3_42_… or rptc_42_….
  3. Backend saves a PENDING record Including what was bought. Then returns the payment_session_id.
  4. Customer pays on checkout UPI, card, netbanking, whatever the gateway offers.
  5. Return + verify, or the webhook Both call the same "grant if paid" function: ask the gateway (Get Order), and if paid, fulfil exactly once.
Tip: one shared "grant if paid" function

Verify and the webhook should call the exact same function, e.g. grantIfPaid(orderId). Two separate implementations drift apart, and one of them ends up missing a check.

Order states vs payment attempts

One order can have several payment attempts. The customer's UPI payment fails, they try a card, and that one succeeds.

  • Order status (e.g. Cashfree: ACTIVE → PAID or EXPIRED) is what you decide on.
  • Payment status (SUCCESS, FAILED, USER_DROPPED, PENDING…) is per attempt. Record attempts in the ledger, but don't mark the whole order failed because one attempt failed.
  • To find which payment succeeded (for the receipt), list the order's payments and pick the one with SUCCESS.
  • Set an order expiry when creating it, so unpaid orders close cleanly instead of staying open for a long default period.

Before creating: eligibility

Check business rules before taking money. Refunding is much harder than saying no.

PurchaseExample rules
Extra family slotOnly on the plan that offers it; only the next slot (3 before 4); not above the maximum.
Report couponPaid plans only; only if they don't already hold an unused coupon; only after the included monthly reports are used up.
  • Same protections as Lesson 6: user from the token, rate limit, per-user lock, price from server config, customer details from the database.
  • Reuse an unpaid order for the same item if one was created minutes ago, instead of creating a pile of them.
  • If an eligibility check itself errors (e.g. a database query fails), decide deliberately. For purchases, "fail closed" (don't sell) is usually safer than "skip the check".

Remember what was bought

When the payment succeeds, possibly minutes later via a webhook, you must know exactly what to deliver. Store it on the pending record at creation time:

  • The item type and details: "family slot, target = 3" or "report coupon, valid 3 months".
  • The amount and currency you charged.
  • The user it's for.

Use proper columns (e.g. item_type, item_value), not text tucked into an unrelated field that has to be parsed back out later. Never rely on the client to tell you again what they bought.

Verifying a one-time order

Before fulfilling, check all of these:

  • The order exists in your records (and belongs to this user, if called from verify)
  • The gateway says the order is PAID (Get Order), not just "a payment succeeded" in a webhook payload
  • The paid amount and currency equal what you stored for this order
  • It hasn't already been fulfilled (it's fine if it has: just return the earlier result)

If it's not paid yet: reply "pending", change nothing (same rule as Lesson 7).

Fulfilling exactly once

Verify and the webhook can both reach "fulfil" at the same moment. There are two kinds of things you deliver, and each has a natural way to stay safe:

Kind 1: change an entitlement

Family slots, credits, feature unlocks.

❌ slots = slots + 1: run twice, you get two slots.

✅ slots = max(slots, 3): run twice, still 3.

Write it as "make sure it's at least X", which is naturally safe to repeat.

Kind 2: issue a new item

Coupons, vouchers, licence keys.

Each order must produce exactly one item. Put a UNIQUE constraint on orderId in the items table.

The second attempt's insert fails with "duplicate order", so fetch and return the item that already exists.

Then mark the order fulfilled with a conditional update ("set SUCCESS where not already SUCCESS"). Ideally the item insert and the status update happen in one transaction, so you can never end up "paid and marked done, but no coupon".

Edge case: two different "duplicate" errors

When inserting a coupon, a duplicate error can mean two very different things. The code collided with an existing code: generate a new code and try again. Or the order already has a coupon: stop and return the existing one. If your retry loop treats both the same, it either issues two coupons for one order, or retries until it gives up and tells a paying customer "something went wrong". Check which constraint failed.

Coupon codes done right

Generating

  • Secure randomness. Use the crypto library (crypto.randomInt / randomBytes), not Math.random(), whose output can be predicted.
  • Long enough to be unguessable. 5 letters gives a few hundred million combinations, which is fine for codes tied to one owner but thin for codes anyone can redeem. 8–12 characters is a comfortable default.
  • Easy to read and type. Leave out look-alikes (0 O, 1 l I). Uppercase only avoids case confusion, e.g. RPT-7K4M-Q9XH.
  • UNIQUE on the code column, with a retry on collision.

Owning and redeeming

  • Owned coupons (bought by a user) store that user's ID. Only they can redeem them.
  • Promo coupons (no owner) need stronger codes and maybe per-user limits.
  • Expiry is stored on the coupon and checked at redemption.
  • Redeem atomically: UPDATE coupons SET used = 1 WHERE code = ? AND used = 0 AND (owner IS NULL OR owner = ?) AND expires_at > NOW(). Continue only if 1 row changed. Checking "is it used?" and then marking it used in a separate step lets two quick clicks use one coupon twice.
  • If the thing the coupon pays for fails (e.g. report generation crashes), decide whether the coupon is returned. Usually yes: mark it unused again, or mark it used only when the work succeeds.

When things change between paying and delivering

Eligibility was checked at order creation. By the time the payment lands, things may have changed:

What changedExampleSensible handling
Plan changedBought a Starter-only slot, then upgraded or expired before payingHonour it (the payment is real), or refund automatically. Never silently keep the money.
Bought twiceTwo tabs, both paid for "slot 3"The second can't be fulfilled meaningfully → refund it, or convert it to the next item.
Already holds an unused couponTwo coupon orders paid in parallelIssue both (they paid for two) or refund one. Pick a policy and log it.

Once money is taken, either deliver what was paid for or give it back, and log which.

Failed and abandoned orders

  • Pending ledger rows are created for every order. Many will never be paid. That's normal.
  • Failed / dropped webhooks update the attempt in the ledger (with the reason) without failing the order.
  • A cleanup job marks orders past their expiry as EXPIRED, so "pending" doesn't mean "forever unknown".
  • Reporting: paid vs expired orders shows how many people start and don't finish, and where they drop off.
