Lesson 5

Idempotency

A long word for a simple idea: asking for the same thing twice should have the same effect as asking once. In payments, this is what makes retries safe.

The problem: the lost response

Your server asks the gateway to create something. The gateway does it, but the reply never reaches you.

Your server is stuck: it doesn't know whether the subscription exists. Retrying blindly might create a second one. Not retrying leaves the customer with an error even though everything worked. Idempotency solves exactly this.

What idempotent means

An action is idempotent if doing it many times gives the same result as doing it once.

ActionIdempotent?Why
Read a subscription's statusNaturallyReading changes nothing.
"Set status to CANCELLED"MostlyCancelled twice is still cancelled; the second call may just error.
"Create a subscription"NoEach call makes a new one.
"Charge ₹499"NoEach call takes money again.
"Add 1 month to access"NoTwice gives two months.

The non-idempotent ones need protection, and that's what an idempotency key provides.

Unique ID vs idempotency key

When creating a subscription you send two values that both look like "unique IDs". They do different jobs:

Your subscription ID

A business rule: "no two subscriptions may share this ID".

Send it again → error: already exists.

Lasts forever.

Idempotency key

A retry rule: "I'm asking the same thing again".

Send it again with the same request → the original response, replayed.

Kept only for a short time.

Your subscription ID is like a passport number: it identifies one thing, forever, and no two can match. The idempotency key is like a receipt number at a counter: show the same receipt again and the clerk says "already done, here's your copy", instead of doing the work twice.

The key itself is just a string you generate, usually a random UUID. Nothing special about it except how the gateway treats it.

How it works inside

Context

Gateways don't publish their internals. This is the common industry pattern (Stripe documents it openly), and it's the right mental model.

Picture two separate tables at the gateway:

Table 1: subscriptions (the real data)

subscription_id (unique)customerstatus
sub_42PriyaINITIALIZED

Table 2: idempotency notebook (for retries only)

idempotency_key (unique)request fingerprintsaved responseexpires
K1hash of the request body{ session_id: "subs_token_xyz", … }~24h

When a request arrives with a key, the gateway checks the notebook first:

  1. Key not in notebook → new request. Do the work, then save key + fingerprint + response.
  2. Key found, same fingerprint → a retry. Don't touch Table 1; return the saved response.
  3. Key found, different fingerprint → you reused a key for a different request. Reject with 422.

Walkthrough: four retry scenarios

The first request created sub_42, but the response was lost. Now you retry:

Retry sendsWhat the gateway doesResult
Same ID sub_42, same key K1Finds K1 in the notebook, replays the saved responseSuccess; same session as before
Same ID sub_42, no keyTries to insert sub_42, which already exists400: already exists
Same ID sub_42, new key K2K2 is new, so it tries to insert sub_42, which exists400: already exists
New ID sub_43, no keyCreates a brand-new subscriptionWorks; sub_42 is left unused and expires
Is the leftover sub_42 a problem?

For creating a subscription: no. Creating moves no money. The customer only pays on the session you actually open, so the unused one stays INITIALIZED and later expires. Its webhooks (if any) find no matching row in your database and are ignored. It just clutters the dashboard. For charges and refunds, the same mistake means real money moving twice.

Without a key, you can still do it by hand

  1. Send the create request.
  2. If it fails with "already exists", fetch it by your ID (GET /subscriptions/sub_42).
  3. Use the session ID from that response.

It works, but needs an extra call and more error handling. The key does the same in one step.

Why not just use the unique ID?

"If the ID already exists, why not just return it?" Good question. Four reasons it's built separately:

  1. A duplicate ID might be a bug, not a retry. Two different users accidentally given the same ID, maybe with different plans. Quietly returning the old one would hide a serious problem. The key makes your intent explicit.
  2. Many actions have no ID of yours. "Cancel this subscription" or "charge ₹499" don't create a row with your unique ID. A key works on any request.
  3. Many requests per object. One subscription gets a create, several charges, a cancel, each with its own key. That fits a separate table (many rows), not one column.
  4. Different lifetimes. Subscription data lives forever; retry records are only useful for minutes or hours and can be cleaned up.

For one endpoint, a column would be enough. As a feature across the whole API, a separate table is cleaner.

Rules for using keys

  • One key per action. Generate a fresh key for each new thing you want done.
  • Reuse it only for an identical retry. Same endpoint, same body. A different body with the same key gets 422.
  • Never reuse a key for a different action, e.g. using the "create" key to "cancel". You might get the old create response replayed.
  • Keys expire (commonly about 24 hours; check your gateway). A retry after expiry is treated as brand new.
  • Usually a UUID. Docs often ask for UUID format. If you want it tied to your ID, derive it deterministically (UUID v5 of your order ID): the same order always gives the same key.
  • Store it if the retry may happen later. If retries happen in a background job hours later, save the key with the job so the retry uses the same one.

When it really matters

Ask: "If this request runs twice by accident, does something bad happen?"

Request typeExampleTwice by accidentKey needed?
ReadFetch statusSame data twiceNo
CreateCreate subscription or orderDuplicate, or "already exists"Helpful
Move moneyCharge, refundCharged or refunded twiceEssential
Change stateCancel, pauseSecond call errorsNice to have
One-time developer setupCreate a plan from a script"Already exists"; just check and re-runNot needed

Your side needs it too

Idempotency isn't only something you ask of the gateway. Your own endpoints receive repeats as well:

  • Webhooks arrive more than once. Gateways retry until you reply 200, and sometimes send duplicates anyway. Processing "payment succeeded" twice must not extend access twice. Record each gateway payment ID once (a unique column) and skip ones you've seen.
  • Return URL and webhook race. Both report the same success. Grant access with an atomic "only if not already granted" update.
  • Users double-click. Your "create" endpoint must not create two subscriptions (Lesson 6).

In a payment system, assume every message can arrive twice, late, or not at all, and design so that none of those cause harm.
