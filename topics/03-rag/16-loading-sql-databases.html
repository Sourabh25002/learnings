Section 3 · Lesson 16

Loading SQL Databases

Company data often lives in a SQL database: tables of rows and columns that link to each other. The challenge is keeping those links when turning tables into Documents. (NoSQL databases like MongoDB return JSON-like data, so Lesson 15 applies.)

The sample database

A SQLite file, data/databases/company.db, with two linked tables:

employees

id          INTEGER PRIMARY KEY
name        TEXT
role        TEXT
department  TEXT
salary      REAL

John Doe, Jane Smith, Mike Johnson, Sarah Williams

projects

id       INTEGER PRIMARY KEY
name     TEXT
status   TEXT
budget   REAL
lead_id  INTEGER   → employees.id

4 projects, led by John, Jane, Mike and Jane.

lead_id holds the id of the employee leading each project: that's the link.

Method 1: inspect with SQLDatabase

from langchain_community.utilities import SQLDatabase

db = SQLDatabase.from_uri("sqlite:///data/databases/company.db")

print(db.get_usable_table_names())   # ['employees', 'projects']
print(db.get_table_info())

from_uri connects (a URL for a cloud database); get_table_info() shows each table's definition (its CREATE TABLE statement) and first 3 rows. Useful for looking around, but it doesn't produce Documents.

Method 2: one Document per table

import sqlite3
from typing import List
from langchain_core.documents import Document


def sql_to_documents(db_path: str) -> List[Document]:
    """Convert SQL database to documents with context"""
    conn = sqlite3.connect(db_path)
    cursor = conn.cursor()
    documents = []

    # Get every table in the database
    cursor.execute("SELECT name FROM sqlite_master WHERE type='table';")
    tables = cursor.fetchall()

    for table in tables:
        table_name = table[0]

        # Column names
        cursor.execute(f"PRAGMA table_info({table_name});")
        columns = [col[1] for col in cursor.fetchall()]

        # All rows
        cursor.execute(f"SELECT * FROM {table_name};")
        rows = cursor.fetchall()

        table_content = f"Table: {table_name}\n"
        table_content += f"Columns: {', '.join(columns)}\n"
        table_content += f"Total Records: {len(rows)}\n\nSample Records:\n"
        for row in rows[:5]:
            table_content += f"{dict(zip(columns, row))}\n"

        documents.append(Document(
            page_content=table_content,
            metadata={
                "source": db_path,
                "table_name": table_name,
                "num_records": len(rows),
                "data_type": "sql_table",
            },
        ))

    conn.close()
    return documents

sql_docs = sql_to_documents("data/databases/company.db")   # 2 Documents

The function lists the tables, reads each one's columns and rows, and writes them as readable text. Result: 2 Documents (employees, projects), with the table name and record count in metadata.

Only 5 rows

rows[:5] writes just the first 5 rows. Fine here, but on a real table every later row would never reach the vector database, so it could never be found.

Adding relationship Documents

Per-table Documents keep employees and projects apart, but "Which projects does Jane Smith lead?" needs both. A JOIN (a query combining rows from two tables where a value matches) builds a Document about the relationship: 

    # Strategy 2: relationship documents (inside sql_to_documents, before conn.close())
    cursor.execute("""
        SELECT e.name, e.role, p.name AS project_name
        FROM employees e
        JOIN projects p ON e.id = p.lead_id
    """)
    relationships = cursor.fetchall()

    rel_content = "Employee-Project Relationships:\n\n"
    for name, role, project_name in relationships:
        rel_content += f"{name} ({role}) leads {project_name}\n"

    documents.append(Document(
        page_content=rel_content,
        metadata={
            "source": db_path,
            "data_type": "relationship",
            "query": "employee_project_join",
        },
    ))

Each project's lead_id is matched to an employee's id, giving lines like "Jane Smith (…) leads …". Now there are 3 Documents.

Takeaways

  • Turn tables into readable Documents with your own queries.
  • Add relationship Documents (JOINs) so linked facts are stored together.
  • Rich content and metadata make retrieval work; split further if needed.
