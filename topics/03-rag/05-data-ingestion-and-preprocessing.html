Section 2 · Lesson 5

Data Ingestion and Preprocessing

A RAG pipeline has three core components: document ingestion, query processing and generation. This lesson is the first: getting your data into the vector database. It happens in advance, before anyone asks a question.

What goes in

Whatever the RAG system should know about (company data, policy documents, any external data), from any source: PDFs, Word documents, CSV files, websites, images, databases.

Document ingestion: reading data from all these sources through a data ingestion pipeline, preprocessing it, and storing it in a vector database.

  1. LoadRead the data from its source.
  2. SplitCut it into chunks.
  3. EmbedTurn each chunk into a vector.
  4. StoreSave the vectors in a vector database.

Split into chunks

A chunk is a small piece of a document. The data is cut into chunk 1, chunk 2, chunk 3…:

Document  →  [ chunk 1 ] [ chunk 2 ] [ chunk 3 ] …

The cutting is done by a text splitter (also called a document splitter); Section 3 shows how.

Why chunk?

Every LLM has a limit on its context size: how much text it can take in at once and still answer well. The limit differs between models.

"Here's a 1,000-page book: use it to answer my question." Some LLMs can take that in; others manage only about 500 pages. Chunking means only the few relevant pieces are sent, not the whole book.

It also makes retrieval sharper: a small, focused chunk matches a specific question far better than a whole document does. But there's a trade-off: chunks that are too small lose the surrounding context, and chunks that are too large mix several topics together. Choosing the size is one of the main decisions in RAG (Lesson 10).

Turn chunks into vectors

A vector is a list of numbers that represents the meaning of a piece of text:

"some sentence from the chunk"  →  [0.6, 0.5, 0.4, 0.1, 0.7, …]

An embedding model does the conversion: a model trained so that texts with similar meanings get similar numbers (an idea from NLP). The course uses models from OpenAI and Hugging Face.

Store the vectors

A vector database stores the vectors and can quickly find the ones closest to a given vector. The course uses FAISS, ChromaDB, DataStax and Pinecone (one of the most common) (what each is).

What this makes possible

With everything stored as vectors, a question can be matched against them using similarity search, measured with cosine similarity or Euclidean distance (two ways of measuring how close two vectors are).

A PDF about LLMs has been ingested. You ask "What is LLM?", and cosine similarity finds the chunks of that PDF that match.

Takeaways

  • Ingestion = load → split → embed → store, done in advance.
  • Chunks fit the LLM's context limit and make retrieval precise; their size is a trade-off.
  • Embeddings turn meaning into numbers; the vector database finds the closest ones.
