Lesson 7

Embeddings

An embedding turns a piece of text into a list of numbers that represents its meaning. Texts that mean similar things get similar numbers. That's what lets the Vault find the chunk about "closing balance" even when the question uses different words.

In this lesson
  1. What an embedding is
  2. Why numbers make search work
  3. The model we use

What an embedding is

"01-09-26 Salary 50,000 ... Closing Balance: 35,000"
        ↓  embedding model
[0.021, -0.113, 0.087, 0.004, ..., -0.056]      (768 numbers)

You can't read meaning from any single number. Together, they place the text at a point in a "meaning space". Texts about similar things land close together; unrelated texts land far apart.

Map coordinates. Two places with close latitude and longitude are near each other, even if they have completely different names. An embedding is coordinates for meaning, just with 768 directions instead of 2.

Why numbers make search work

A plain word search for "closing balance" misses a chunk that says "Balance at end of period". With embeddings, the question is turned into numbers too, and the search looks for chunks whose numbers are closest to the question's numbers. Close numbers mean close meaning, so the right chunk is found even with different words.

Chunks are embedded once, when the file is processed. Each question is embedded at chat time. Both must use the same model, or their numbers can't be compared.

The model we use

Detail
ModelBAAI/bge-base-en-v1.5, set by the EMBEDDING_MODEL env variable
Output768 numbers per text
LibraryFastEmbed
Where it runsLocally on our server. No API calls, no cost per use
DownloadThe Dockerfile downloads it at build time, so it's ready immediately
CPU useLoaded with threads=1; the Dockerfile also caps AI libraries at 2 threads, to protect the web server sharing the container

The alternative is an embedding API (Gemini, OpenAI): less load on our server, but a cost per call and a network round trip.

Loading the model once

getEmbeddingModel() in rag/indexer.py:

  1. Already loaded? Reuse it. It's kept in a global variable (a singleton), so it's loaded once per program run.
  2. Otherwise, try the preferred model (bge-base).
  3. If that fails, try the fallback, bge-small-en-v1.5 (EMBEDDING_FALLBACK_MODEL).
  4. If both fail, raise an error.

Since the worker exits after every run, it loads the model again on each cron run. The web server keeps its copy for as long as it's running.

Embedding in batches

Chunks are embedded 24 at a time (EMBEDDING_BATCH_SIZE; the code's default is 32, the Dockerfile sets 24). 4 chunks = 1 batch; 100 chunks = 5 batches.

for each batch of 24:
    numbers = model.embed(batchTexts)          # 24 texts → 24 lists of 768 numbers
    convert to plain Python floats              # what ChromaDB expects
    collection.add(texts, numbers, metadata, ids)
    log "Indexed batch 1/5 ..."

Why batches? Embedding 500 chunks at once could use a lot of memory. Small batches keep memory low and steady, which matters in a container shared with the web server.

The fallback model trap

Edge case: two models, two sizes

The preferred model gives 768 numbers; the fallback gives 384. A document indexed with one can't be searched with the other: the lists don't even have the same length. If the web server ever fell back to the small model while documents were indexed with the base one (or the other way round), search would break with confusing errors. The fallback is a safety net that can cause its own failure.
