Lesson 3

Uploading a file

Everything starts with POST /upload in routes/vaultRoutes.py. It does only two things: put the file in S3, and write a database row saying "pending". No text extraction, no AI. That's left to the background worker.

The Vault endpoints

All 9 endpoints in vaultRoutes.py, grouped by the life of a document:

StageEndpointJob
Upload/uploadSave files to S3, DB status "pending"
Processing/vault/internal/pendingThe worker asks "which files are waiting?"
Processing/vault/internal/update_statusThe worker reports processing / completed / error
Status/list_uploadsAll of a user's files and their statuses
Status/file_statusOne file's status
Chat/load_indexPre-load a document's index so the first chat is fast
Chat/vault_llm_chatAsk a question (normal or streamed)
Delete/delete_filesRemove from ChromaDB, S3 (PDF and index) and the DB
Other/ocrInternal PDF-to-text tool. Not part of the Vault flow

The two /vault/internal/... routes and /ocr use @requireInternalAuth (a secret key) instead of @requireAuth (a user's login). They're for other programs, not for users.

What the frontend sends

The Vault page (aumsampaan/src/pages/Vault/Vault.tsx) sends a multipart/form-data request, built with FormData in services/vaultService.ts:

FieldValueRead in Python with
filesOne or more PDFsrequest.files.getlist("files")
userIdThe user's IDrequest.form.get("userId")
userNameThe user's first namerequest.form.get("userName")

getlist returns all files; plain .get would return only the first. The frontend also checks: PDFs only, at most 5MB each, and a maximum number of pages.

The upload, step by step

  1. Auth check @requireAuth verifies the login token before the function runs.
  2. Read the request userId, files, userName.
  3. Basic checks No files → 400 "No files provided". No userName → 400 "userName is required".
  4. Early quota check Is the user already at 100MB? Then reject straight away. (See below.)
  5. Prepare each file Clean the file name (sanitizeFilename, so names like ../../hack.pdf can't touch server folders). Build a unique S3 name: vaultFile/{userId}_{timeInMilliseconds}.pdf. Save the file into its own temporary folder and measure its real size.
  6. Real quota check Do all these files together fit in the remaining quota?
  7. Upload each file Upload to S3, count the PDF's pages, insert a row in vaultFiles with status pending, log it.
  8. Add to the user's usage incrementUsage adds the uploaded bytes to the quota.
  9. Reply {"message": "Upload complete. Files will be processed in background."}
  10. Clean up, always A finally block deletes every temp file and folder, whether the upload worked or not.

The upload is "fast" because it only stores the file. The slow work happens later, in the worker.

Why save to a temp folder first?

Before a file is saved, Flask often reports its size as 0. Saving it to disk gives the real size, which the quota check needs. It also gives the page counter a real file to open.

The 100MB quota

This part is my own work: commit "100MB file size limit implementation", 11 Sep 2026. It added services/fileQuota.py and restructured the upload into two passes.

Each user has a lifetime limit of 100MB, stored in the userFileQuota table (one row per user: usedBytes, limitBytes).

FunctionWhat it does
getQuota(userId)Reads used and limit. No row yet means 0 used.
checkQuota(userId, bytes)"Would these bytes fit?" Returns allowed, remainingBytes, message. Never changes anything.
incrementUsage(userId, bytes)Adds bytes to usedBytes, creating the row if needed. Only called after a successful upload.

Why there are two checks

CheckQuestionWhy
checkQuota(userId, 1)"Is there any space left?"The real sizes aren't known yet, so it asks about 1 byte. If the user is already full, reject before doing any work.
checkQuota(userId, totalBytes)"Do these exact files fit?"After saving and measuring them.

The first check is a shortcut: fail fast before doing expensive work.

Before and after my change

Before (one loop)

For each file: save to temp, upload to S3, save to DB, clean up. No size checks. The S3 name used userName.

After (two passes)

Early check → save and measure all files → real check → upload all → count usage → clean up everything in one finally. The S3 name uses userId.

The vaultFiles table

One row per uploaded file. All its SQL is in core/metaFiles.py.

ColumnHolds
idRow ID
userIdWho uploaded it
fileNameOriginal name, e.g. statement.pdf
s3KeyWhere the PDF is in S3
fileSizeMb, totalPagesSize and page count
statuspending / processing / completed / error
uploadedAt, processedAtWhen uploaded, when processing finished
chunkCountHow many chunks it became
indexS3KeyWhere its search index is backed up in S3
errorMessageWhy it failed

The insert uses ON DUPLICATE KEY UPDATE: if a matching row already exists (it looks like one row per user + file name), it's overwritten and reset to pending instead of creating a second row.

What's done well

  • Temp files are always cleaned up (finally)
  • File names are sanitized
  • Each file gets its own temp folder, so two files with the same name don't clash
  • Quota is checked before work, and usage is only counted after success
  • It replies fast and leaves heavy work to the background

Gaps and edge cases

Things that can go wrong
  • A user can upload into someone else's account. The route uses the userId sent by the frontend, not g.userId from the login token. Change userId in the request and the file lands in another user's vault, using their quota.
  • The backend doesn't check the file. PDF-only, 5MB and the page limit are only checked in the frontend. Calling the API directly (Postman, a script) can upload any file type or size.
  • Re-uploading the same file name leaves garbage. The DB row is overwritten with the new S3 name, so the old PDF and its old index stay in S3 forever with nothing pointing to them. The quota counts both.
  • Half-finished uploads. With 3 files, if file 3 fails, files 1 and 2 are already uploaded but the user sees an error. They retry and create duplicates. The quota isn't increased for files 1 and 2 either, because the error skips that step.
  • S3 succeeds, DB fails. The PDF sits in S3 with no record of it.
  • Same-millisecond names. Two small files saved within the same millisecond get the same S3 name, and one overwrites the other. Adding a random part (UUID) fixes it.
  • userName is required but never used. It used to be part of the S3 name. My quota change switched that to userId, and the check stayed behind. A user with no first name can't upload at all.
  • Two uploads at the same moment can beat the quota. Both check "is there space?", both see yes, and both upload. Rare and low impact.
