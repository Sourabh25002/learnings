Lesson 6

Chunking

Chunking means cutting each page's text into small pieces, so that later we can find just the relevant piece for a question instead of handing the AI a whole document. It's the first step of indexDocument in rag/indexer.py.

Why chunk?

When the user asks "what's my closing balance?", the answer is in one or two lines of one page. If each searchable unit were a whole document, search could only say "it's somewhere in this file". Small pieces make search precise: it can return the exact few pieces that matter, and only those are sent to the AI.

Index cards instead of a book. To answer a question you pull out the 5 most relevant cards, rather than photocopying the whole book.

The trade-off: pieces too big contain lots of unrelated text; pieces too small lose context (a number without the sentence explaining it).

How a page becomes chunks

  1. Skip empty pages No content → move on.
  2. Split into paragraphs Cut wherever there's a blank line (\n\n) and drop empty pieces. pdfplumber usually separates lines with a single newline, so in practice a whole page often comes out as one big paragraph.
  3. Table or text? A paragraph starting with | is treated as a table and kept as one whole chunk, never cut. Everything else is text.
  4. Cut long text 1,000 characters or less → one chunk. Longer → the sliding window below.
  5. Label each chunk Attach the file name, page number, position and type.

Sliding window and overlap

  1. Take characters 0 → 1,000.
  2. Don't cut a word in half: move the cut back to the last space, as long as that's past the halfway point.
  3. Start the next chunk 200 characters before the previous one ended.
  4. Repeat until the end of the text.
A 2,300-character page:
Chunk 0:  characters     0 → ~1,000
Chunk 1:  characters  ~800 → ~1,800     (starts 200 before chunk 0 ended)
Chunk 2:  characters ~1,600 → 2,300

Overlap exists because a sentence that falls exactly on a cut would be split between two chunks, and neither half would make sense alone. With 200 characters of overlap, it appears whole in at least one chunk.

Metadata and IDs

Every chunk carries a label:

{
  "text": "01-09-26 Salary 50,000\n05-09-26 Rent -15,000 ...",
  "metadata": {
    "documentName": "hdfc_statement.pdf",   # readable name (displayName), not the docName
    "pageNumber": 2,
    "chunkIndex": 1,                         # 2nd chunk on this page; restarts at 0 each page
    "contentType": "text"                    # or "table"
  }
}

The metadata is how a chat answer can say "Source: hdfc_statement.pdf, page 2".

Each chunk also gets a unique ID:

{docName}_p{page}_c{chunkIndex}_{8 random characters}
42_1760345678123_p2_c1_c81b9a03

The random part (from uuid) guarantees no two IDs are ever the same.

A worked example

hdfc_statement.pdf, 2 pages: page 1 is short (~200 characters), page 2 is long (~2,300 characters of transactions).

PageLengthChunks
1~200 chars1 chunk (fits in 1,000)
2~2,300 chars3 overlapping chunks

Result: 4 chunks, each with text and metadata. If there were none, indexDocument would return 0 straight away.

indexer.py vs chunker.py

There are two chunking implementations. Only one runs.

rag/indexer.py (used, Jun–Aug 2026)

  • Size in characters: ≤1,000, 200 overlap
  • Splits on blank lines
  • Keeps | blocks whole as tables

rag/chunker.py (unused, Feb 2026)

  • Size in tokens (how AI models count text), aiming for ~350
  • Detects financial sections ("Balance Sheet", "Cash Flow", "Risk Factors") and tags chunks with them
  • Detects tables and keeps them whole
  • Built for Docling, an older PDF reader the team replaced

When the pipeline was rebuilt, the new chunking was written inside indexer.py and chunker.py was never deleted. Its ideas (tokens, sections) are good candidates to bring back.

Things worth noticing

Weak spots
  • Characters, not tokens. AI models measure text in tokens, so token-based sizing is more precise.
  • Whole pages are often one paragraph, so chunks are cut purely by the 1,000-character window, not at natural boundaries like headings.
  • The table rule rarely triggers. pdfplumber's text has tables as space-separated lines, not |. The | format only exists in the table data the Vault throws away.
