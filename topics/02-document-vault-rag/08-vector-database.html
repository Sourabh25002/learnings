Lesson 8

Storing vectors: ChromaDB and S3

Once chunks are turned into numbers, they need to be stored somewhere that can answer "which chunks are closest to this question?". That's a vector database. The Vault gives every document its own small ChromaDB database, and backs it up to S3.

What a vector database is

A vector is just a list of numbers, like an embedding. A vector database stores those lists next to their text, and answers one special question fast: "give me the stored items whose numbers are closest to these numbers". A normal database answers "find rows where X equals Y"; a vector database answers "find rows that mean something similar".

ChromaDB: a database that's just a folder

client = chromadb.PersistentClient(path="data/chromadb/42_1760345678123")
collection = client.get_or_create_collection(name="financial_documents")
  • PersistentClient saves to disk in that folder, not just in memory. Like SQLite: the whole database is files in a folder.
  • A collection is like a table. Ours is called financial_documents.

Each chunk becomes one record:

iddocument (text)embeddingmetadata
..._p2_c1_c81b9a03"01-09-26 Salary..."[0.021, -0.113, ...]{documentName, pageNumber: 2, chunkIndex: 1, contentType}

One database per document

data/chromadb/
├── 42_1760345678123/     ← one user's statement
├── 42_1760399990000/     ← the same user's contract note
└── 77_1760412345678/     ← another user's file
  • Isolation: one user's chunks can never show up in another user's search.
  • Easy delete: deleting a document = deleting its folder.
  • Easy backup: one folder = one upload to S3.

The cost: chat has to open (and maybe download) a separate database for each document it searches. Lessons 9–10 cover that side.

indexDocument's storage steps

  1. Prepare 3 parallel lists ChromaDB wants texts, metadatas and ids as separate lists, in the same order.
  2. Fresh folder data/chromadb/{docName}/. If it already exists (the file is being re-processed), delete it first, so old and new chunks never mix.
  3. Open ChromaDB A PersistentClient in that folder, collection financial_documents.
  4. Embed and add, in batches of 24 collection.add(documents, embeddings, metadatas, ids). Lesson 7.
  5. Close it del client / del collection release the connection, making sure everything is written to disk before the folder is uploaded.
  6. Upload the folder to S3 If that fails, raise an error, and the worker marks the file "error".
  7. Return the chunk count Logged as "Document '...' indexed (4 chunks) and backed up to S3."

Backing up to S3

uploadDirToS3 in rag/s3Storage.py walks through every file in the folder and uploads each one, keeping the same structure:

data/chromadb/42_1760345678123/chroma.sqlite3
    → s3://<bucket>/vaultFile/42_1760345678123/chroma.sqlite3

Why? The server's disk isn't permanent: on a restart or redeploy, local files can disappear. S3 keeps the index safe, and chat can download it whenever it's needed. s3Storage.py also has downloadDirFromS3 (used by chat) and deleteIndexFromS3 (used by delete).

Marking the file completed

Back in the worker:

indexS3Key = f"vaultFile/{docName}/"
apiUpdateStatus(fileId, "completed", chunkCount=chunkCount, indexS3Key=indexS3Key)

The whole of indexDocument

pages (text per page)
  ├─ 1. chunkDocument → ≤1000-char chunks, 200 overlap, with metadata     (Lesson 6)
  ├─ 2. no chunks? → return 0
  ├─ 3. build 3 lists: texts, metadatas, ids
  ├─ 4. fresh folder: data/chromadb/{docName}/
  ├─ 5. open ChromaDB in that folder
  ├─ 6. load the embedding model (once)                                   (Lesson 7)
  ├─ 7. batches of 24: text → 768 numbers → collection.add
  ├─ 8. close the database (flush to disk)
  ├─ 9. upload the folder to S3: vaultFile/{docName}/
  └─ 10. return the chunk count

Gaps

Things that can go wrong
  • 0 chunks still means "completed". If nothing was indexed, indexDocument returns 0 without an error, and the worker marks the file completed with nothing to search.
  • Local folders are never deleted after upload. The server's disk slowly fills with indexes.
  • indexS3Key is built by hand. The worker copies the naming pattern from s3Storage.py instead of getting the real path back. If someone changes the pattern there, the database points to the wrong place. Cleaner: have indexDocument return the path it used.
