Lesson 4

The background worker

After an upload, the file just sits in S3 marked "pending". The background worker, processVaultFiles.py, picks it up within 5 minutes, extracts the text, indexes it and marks it "completed". This lesson covers how it's scheduled, how it avoids running twice, and what each of its functions does.

Why a background worker?

Extracting text and creating embeddings for a PDF can take from a few seconds to a few minutes. If the upload request did that work, the user would stare at a spinner, and the request could time out. So the upload replies immediately, and a separate program does the heavy work later.

Where the schedule lives

The schedule isn't in the Python code. processVaultFiles.py only knows what to do. Linux's built-in cron decides when.

Node.js way

The timer lives inside your app:

// app.js
cron.schedule("*/5 * * * *",
  () => processFiles());

This project

The timer is Linux's cron, set up in the Dockerfile. Every 5 minutes it starts the script as a fresh program.

1. The rule: Dockerfile, line 37

*/5 * * * * appuser /usr/local/bin/python /app/processVaultFiles.py >> /var/log/vault-processor.log 2>&1

2. Keeping cron running: supervisord.conf

[program:cron]
command=/usr/sbin/cron -f
autostart=true
autorestart=true

supervisord starts cron when the container starts and restarts it if it crashes. The same file starts gunicorn (the web server).

Tip: where to find the worker's logs

In /var/log/vault-processor.log inside the container, not in the normal Docker logs. Easy to miss when debugging.

Other schedulers

The file's docstring mentions Windows Task Scheduler, cron, systemd timers and a keep-alive loop. They're all tools that run a program on a schedule; it's saying "use whichever your system has". This project runs on Linux, so it's cron.

Why a separate program?

Why not a timer inside the Flask app?

  • Crash safety: if processing a bad PDF crashes the worker, only that run dies. The web server keeps working, and cron starts a fresh run 5 minutes later.
  • Memory is freed: the script starts, works and exits. All the memory it used (AI model, PDF data) goes back to the system.
  • No blocking: Python can't run heavy work in parallel well inside one program. Inside Flask, PDF processing would block the threads answering users.
  • No accidental duplicates: the web server can run several copies of the app and restarts them regularly (gunicorn here restarts after 500 requests). A timer inside the app could get duplicated or killed.
  • Easy to test: python processVaultFiles.py runs it by hand.
But it's the same container

The worker and the web server are separate programs, but they share the same CPU and memory. While the worker processes a big PDF, the APIs can get slower. If the worker uses too much memory, the whole container can run out. The Dockerfile limits the AI libraries to 2 CPU threads (OMP_NUM_THREADS=2 and similar), probably for this reason.

The two programs aren't "async" in the Node sense (one program juggling promises). They're two independent programs running at the same time, with the operating system sharing the CPU between them. From the user's point of view, though, the processing is async: the upload doesn't wait for it.

The 7 functions

When cron starts the file, Python reads it top to bottom. Most of it is function definitions, which don't run anything by themselves. Only the last two lines start the work: 

if __name__ == "__main__":     # "if this file was run directly"
    runLoop()

Then the functions call each other:

runLoop()
 ├── _acquireProcessorLock()     take the lock, or exit if another run is busy
 ├── processBatch(10)
 │     ├── apiGetPending(10)     get up to 10 waiting files

 │           └── processFile()   download → extract text → index → mark completed

 └── _releaseProcessorLock()     remove the lock

The lock

Why it's needed

Cron doesn't check whether the last run has finished. Without a lock:

0:00  Run 1 fetches 10 pending files, starts file 1 (a big PDF)
5:00  Run 1 is still on file 1. Files 2–10 are still "pending"
      (each file is only marked "processing" when its turn comes)
5:00  Run 2 starts and fetches "pending" files → gets files 2–10 too!

Two runs would process the same files: double work, double load on the shared container, and both writing to the same index folder at once.

How it works

The lock is just one file: data/vault_processor.lock. File exists → someone is running. No file → free.

  1. Try to create the lock file os.open(path, O_CREAT | O_EXCL | O_WRONLY) means "create this file, but only if it doesn't exist". The operating system does this as one all-or-nothing step, so even two runs at the same instant can't both succeed.
  2. Created? I'm the only one Write a small note inside ({"pid": 12345, "createdAt": ...}, just for debugging) and continue.
  3. Already exists? Check its age Under 2 hours old: another run is working, so log "already running" and exit. Over 2 hours: the old run probably crashed without cleaning up, so delete the lock, create a new one and continue.
  4. When finished, delete it In a finally block, so it happens even if processing failed. 
0:00   Run 1: create lock ✅ → working...
5:00   Run 2: create lock ❌ (exists, 5 min old) → skip
8:00   Run 1: done → delete lock
10:00  Run 3: create lock ✅ → working...

A single key for a meeting room. Whoever has the key uses the room and returns it after. Key missing = room busy. Key missing for 2 hours = someone forgot to return it, so make a new one.

A file is used (not a variable like isRunning = true) because each cron run is a separate program, and separate programs can't share variables. They can all see the same file.

Every lock works this way

All locks have the same 3 parts: acquire (only one can succeed, in one step), release, and expiry (so a crash doesn't block forever). Only where the "key" lives changes:

Lock typeWhere the key livesUsed for
In-memory (mutex)A variable in one programThreads in the same program
File lock (here)A file on diskSeparate programs on one server
Database lockA row or flag in the DBMany servers sharing a DB
Redis lockSET key NX EX 7200Many servers. The most common choice
Only works on one machine

The file lock works because everything is in one container. Workers on several servers would each have their own disk and couldn't see each other's lock file. They'd need a shared lock (Redis or the database), or a queue.

Batches: 10 files, one at a time

  • runLoop calls processBatch(10). (processBatch has a default of 5, but it's never used, because 10 is always passed.)
  • Each run takes at most 10 files. Others wait for the next run.
  • Files are processed one by one in a normal for loop, never in parallel. Simpler, and safer on memory in a shared container. The downside: one slow PDF delays everything behind it.
  • If one file fails, the loop carries on with the next.

Example: 25 files uploaded at once.

Run 1 (0 min):    files 1–10
Run 2 (5 min):    files 11–20
Run 3 (10 min):   files 21–25    → the last user waits 10–15 minutes

If a batch takes longer than 5 minutes, the next cron run hits the lock and skips. So the best case is about 10 files every 5 minutes (~120 an hour). Fine for today's light usage.

Talking to the database through the API

The worker never connects to MySQL itself. It calls 2 internal routes on its own web server (same container, same repo):

processVaultFiles.py  (worker)
   │  GET http://localhost:8080/vault/internal/pending?limit=10
   │  header  X-Internal-Key: <secret>
   ▼
gunicorn web server  →  routes/vaultRoutes.py  →  MySQL vaultFiles table
   │
   ▼
list of pending files back to the worker
Worker functionRoute (in vaultRoutes.py)Database effect
apiGetPendingGET /vault/internal/pendingRows with status pending, or processing for over 30 minutes (stuck), oldest first
apiUpdateStatusPOST /vault/internal/update_statusprocessing: status only. completed: + processedAt, chunkCount, indexS3Key. error: + errorMessage, processedAt

The URL comes from INTERNAL_API_URL (default http://localhost:8080) and the key from INTERNAL_API_KEY. requests is Python's axios; both calls time out after 30 seconds.

apiUpdateStatus is called from 3 places in processFile: at the start (processing), at the end (completed), and on failure (error, message cut to 500 characters).

processFile, step by step

Input: one row from vaultFiles as a dictionary. Output: True or False.

  1. Unpack the row fileId, userId, fileName, s3Key, plus holdingType and password (always empty, see Gaps). tmpPdfPath = None so the cleanup can safely check it later.
  2. Mark "processing" The user sees work has started. If the worker crashes from here on, the file stays "processing", and after 30 minutes the next run picks it up again.
  3. Make the docName vaultFile/42_1760345678123.pdf → 42_1760345678123. This is the document's unique ID in the RAG system.
  4. Download the PDF From S3 into memory, then written to a temp file, because the PDF libraries need a file path. delete=False keeps the file after it's closed; the finally deletes it at the end.
  5. Extract the text extractPdfPageWise → one text per page → numbered pages → drop empty pages → if none left, fail. Lesson 5.
  6. Index it indexDocument: chunk, embed, save to ChromaDB, back up to S3. Returns the chunk count. Lessons 6–8.
  7. Mark "completed" With chunkCount and indexS3Key = "vaultFile/{docName}/". The file is now ready for chat. Return True.
  8. On any error Mark "error" with the message, return False.
  9. Always Delete the temp PDF.

Gaps

Things that can go wrong
  • "No pending files" can be a lie. If apiGetPending can't reach the web server (say it's restarting), it logs the error and returns an empty list, so the next log line says "No pending files". Check for a connection error just above it.
  • Failed status updates are ignored. If the "completed" update fails, the file is fully processed but stays "processing". After 30 minutes it's processed again.
  • holdingType and password are never fetched. The pending-files query doesn't select them. So the pms branch never runs, and password-protected PDFs always fail.
  • Hard-coded fallback key. If INTERNAL_API_KEY isn't set, core/config.py falls back to a default key written in the source code. The internal routes are on the same public port as everything else, so anyone who has seen the code could change file statuses. Safer: refuse to start without the key.
  • Outdated docstrings. The file's docstring mentions process_vault_files.py and options like --batch-size and --loop that don't exist. processFile's docstring says "Textract OCR", which isn't used.

When this stops being enough

For today's light usage, cron + one worker is fine. Revisit when files pile up in "pending", users complain about the wait, or APIs slow down during processing. Then scale step by step:

  1. Own container for the workerSame code, started differently. It can no longer slow down or crash the APIs.
  2. A queue instead of cronThe upload puts "process file 123" on a queue (AWS SQS fits, since the project uses AWS). The worker starts immediately, with no 5-minute wait, gets automatic retries, and no longer needs the lock file.
  3. Many workersThe queue hands out one file per worker, so 5 or 10 can run in parallel, with auto-scaling on queue length.
  4. Lighter processingRemove unused work (Camelot table scans), run embeddings on a GPU or through an API.
  5. A real vector database for chatpgvector, Qdrant or Pinecone, instead of one ChromaDB folder per document downloaded from S3.
What about Inngest?

Inngest is a manager for background jobs: it triggers functions on events, retries them and shows every run in a dashboard. It doesn't run your code on its own servers; it calls your function over HTTP, so the heavy work still runs on your server. It would give instant processing and retries. Alternatives: Celery + Redis (classic Python), AWS SQS + a worker, BullMQ (the Node.js equivalent).
